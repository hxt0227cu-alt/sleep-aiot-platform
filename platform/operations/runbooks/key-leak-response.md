# Runbook: 密钥泄露响应

## 概述

**故障类型**: 安全事件
**严重级别**: Critical (P0)
**响应时间**: 5分钟
**解决时间**: 24小时
**负责人**: 安全团队 / 值班主管

## 故障现象

- 检测到未授权的密钥访问
- 密钥在公开渠道泄露（GitHub、日志、论坛等）
- 异常的 API 调用模式
- 安全扫描发现密钥泄露
- 内部报告密钥泄露

## 紧急响应流程

### 阶段 1: 确认和隔离（0-30分钟）

#### 1. 确认密钥泄露（5分钟）

```bash
# 1. 确认泄露的密钥类型和范围
# 查看安全告警详情
# 确认泄露的密钥 ID/名称

# 2. 评估影响范围
# - 哪些系统使用该密钥
# - 密钥的权限范围
# - 是否有未授权访问的迹象

# 3. 检查访问日志
kubectl exec -n vault vault-0 -- vault audit list
# 查看最近的异常访问
```

#### 2. 立即吊销密钥（10分钟）

```bash
# 1. 吊销泄露的密钥
# Vault 动态密钥
kubectl exec -n vault vault-0 -- vault lease revoke -prefix <lease-prefix>

# 静态密钥（立即轮换）
kubectl exec -n vault vault-0 -- vault write -f transit/keys/<key-name>/rotate

# API Key / Token
# 在对应系统中吊销

# 2. 撤销相关的访问权限
# 撤销使用该密钥的服务账号
# 撤销相关的 IAM 权限

# 3. 通知所有相关团队
# 飞书紧急群通知
# 电话通知安全负责人和工程经理
```

#### 3. 防止进一步泄露（15分钟）

```bash
# 1. 检查是否有数据被访问或导出
# 查看审计日志
# 检查数据库访问日志
# 检查对象存储访问日志

# 2. 限制相关服务的访问
# 临时暂停可疑服务
# 限制网络访问

# 3. 保存证据
# 保存相关日志
# 保存访问记录
# 保存系统状态快照
```

### 阶段 2: 影响评估（30分钟-2小时）

#### 1. 评估数据泄露范围

```bash
# 1. 检查密钥的权限范围
# 该密钥可以访问哪些资源
# 可以执行哪些操作

# 2. 检查未授权访问
# 查看密钥泄露后的访问日志
# 检查是否有异常的数据访问
# 检查是否有数据导出

# 3. 评估数据敏感度
# 哪些数据可能被访问
# 数据的敏感级别（公开/内部/机密/绝密）
# 是否涉及个人信息（PII）
# 是否涉及健康数据（PHI）
```

#### 2. 评估业务影响

```bash
# 1. 哪些服务受影响
# 列出使用该密钥的所有服务
# 评估服务中断的影响

# 2. 用户影响
# 影响多少用户
# 是否需要通知用户

# 3. 合规影响
# 是否涉及数据泄露通知义务
# 是否需要向监管机构报告
# 是否涉及法律责任
```

### 阶段 3: 恢复和修复（2-24小时）

#### 1. 轮换所有相关密钥

```bash
# 1. 生成新密钥
# Vault 密钥轮换
kubectl exec -n vault vault-0 -- vault write -f transit/keys/<key-name>/rotate

# 数据库密码
# 修改数据库密码
# 更新 Vault 中的密码

# API Key
# 生成新的 API Key
# 吊销旧的 API Key

# 2. 更新所有服务配置
# 更新使用该密钥的服务配置
# 滚动重启所有相关服务

# 3. 验证新密钥正常工作
# 测试服务功能
# 验证密钥访问正常
```

#### 2. 修复安全漏洞

```bash
# 1. 修复密钥泄露的根本原因
# 如果是代码泄露：清理代码历史
# 如果是配置泄露：修复配置管理
# 如果是日志泄露：修复日志脱敏
# 如果是人员失误：加强培训和流程

# 2. 加强密钥管理
# 启用更严格的访问控制
# 启用密钥自动轮换
# 加强审计监控
# 启用密钥使用告警

# 3. 安全加固
# 检查其他密钥是否也有泄露风险
# 全面安全扫描
# 加强网络安全控制
```

#### 3. 通知和报告

```bash
# 1. 内部通知
# 通知所有相关团队
# 更新事件状态
# 分享事件时间线

# 2. 用户通知（如需要）
# 如果涉及用户数据泄露，按照法规要求通知用户
# 提供用户保护措施（如密码重置、信用监控）

# 3. 监管报告（如需要）
# 如果涉及个人信息泄露，按照《个人信息保护法》要求报告
# 向相关监管机构报告
# 保留所有证据和记录

# 4. 法律合规
# 咨询法务团队
# 评估法律责任
# 准备法律应对
```

### 阶段 4: 事后复盘（24-72小时）

#### 1. 事件复盘会议

- 整理事件时间线
- 分析根本原因
- 评估响应过程
- 识别改进机会

#### 2. 改进措施

- 短期措施（1周内）
  - 修复直接导致泄露的问题
  - 加强密钥访问监控
  - 更新安全策略

- 中期措施（1个月内）
  - 实施密钥自动轮换
  - 加强代码安全扫描
  - 加强员工安全培训

- 长期措施（3个月内）
  - 重构密钥管理架构
  - 实施零信任架构
  - 建立持续安全监控体系

#### 3. 更新文档

- 更新安全策略
- 更新 Runbook
- 更新应急响应计划
- 更新培训材料

## 密钥泄露分级

| 级别 | 描述 | 响应级别 | 通知要求 |
|------|------|---------|---------|
| P0 | 核心密钥泄露，可能导致大规模数据泄露 | 安全团队 + CTO + 法务 | 立即通知，24小时内监管报告 |
| P1 | 重要密钥泄露，可能导致部分数据泄露 | 安全团队 + 工程经理 | 24小时内通知，评估监管报告 |
| P2 | 一般密钥泄露，影响有限 | 安全团队 | 内部通知，评估影响 |
| P3 | 测试/开发密钥泄露 | 开发团队 | 内部记录 |
