# RPO/RTO 定义

## 概述

本文档定义睡眠监测平台各服务的恢复点目标（RPO）和恢复时间目标（RTO），
作为灾难恢复和业务连续性的核心指标。

## 定义

### RPO (Recovery Point Objective)
- **定义**: 最大可接受的数据丢失时间窗口
- **含义**: 灾难发生后，最多丢失多长时间的数据
- **单位**: 分钟/小时
- **示例**: RPO = 5分钟 表示最多丢失5分钟的数据

### RTO (Recovery Time Objective)
- **定义**: 最大可接受的服务中断时间
- **含义**: 灾难发生后，服务必须在多长时间内恢复
- **单位**: 分钟/小时
- **示例**: RTO = 15分钟 表示服务必须在15分钟内恢复

## 各服务 RPO/RTO 指标

### 核心服务（P0）

| 服务 | RTO | RPO | 优先级 | 说明 |
|------|-----|-----|--------|------|
| MQTT Broker (EMQX) | 5分钟 | 0 | P0 | 设备接入核心，消息不丢失 |
| 后端 API | 15分钟 | 5分钟 | P0 | 用户访问核心 |
| 报警检测服务 | 10分钟 | 1分钟 | P0 | 安全相关，延迟报警有风险 |
| PostgreSQL | 5分钟 | 0 | P0 | 主数据库，同步复制 |
| Redis | 5分钟 | 5分钟 | P0 | 缓存和会话，可重建 |

### 重要服务（P1）

| 服务 | RTO | RPO | 优先级 | 说明 |
|------|-----|-----|--------|------|
| OTA 服务 | 30分钟 | 15分钟 | P1 | 固件升级，短时中断可接受 |
| 数据管道 | 30分钟 | 5分钟 | P1 | 数据处理，可延迟处理 |
| Kafka | 15分钟 | 5分钟 | P1 | 消息队列，有持久化 |
| ClickHouse | 1小时 | 15分钟 | P1 | 分析数据库，可延迟恢复 |
| 前端 Web | 15分钟 | 0 | P1 | 静态资源，CDN 缓存 |

### 一般服务（P2）

| 服务 | RTO | RPO | 优先级 | 说明 |
|------|-----|-----|--------|------|
| 小程序后端 | 30分钟 | 15分钟 | P2 | 非核心功能 |
| 管理后台 | 1小时 | 1小时 | P2 | 内部使用 |
| 日志服务 (Loki) | 4小时 | 1小时 | P2 | 日志可丢失 |
| 链路追踪 (Jaeger) | 4小时 | 1小时 | P2 | 追踪数据可丢失 |
| 监控 (Prometheus/Grafana) | 2小时 | 1小时 | P2 | 监控数据可重建 |

### 安全服务（P0）

| 服务 | RTO | RPO | 优先级 | 说明 |
|------|-----|-----|--------|------|
| Vault | 15分钟 | 0 | P0 | 密钥管理，不可丢失 |
| PKI/CA | 1小时 | 0 | P0 | 证书签发，离线备份 |
| 认证服务 | 15分钟 | 5分钟 | P0 | 用户认证核心 |

## 整体业务指标

### 业务连续性目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 年度可用性 | 99.9% | 全年停机时间 < 8.76小时 |
| 月度可用性 | 99.95% | 每月停机时间 < 22分钟 |
| 单可用区故障 RTO | < 15分钟 | 自动切换 |
| 全区域故障 RTO | < 1小时 | 手动切换到备用区域 |
| 数据丢失 RPO | < 5分钟 | 核心数据 |
| 灾难恢复演练频率 | 每季度 | 验证恢复流程 |

### 分级响应要求

| 故障级别 | 影响范围 | 响应时间 | 解决时间 | 升级路径 |
|---------|---------|---------|---------|---------|
| P0 (紧急) | 核心服务完全不可用 | 5分钟 | 30分钟 | 值班 → 主管 → 经理 → CTO |
| P1 (高) | 重要服务故障或性能严重下降 | 15分钟 | 2小时 | 值班 → 主管 → 经理 |
| P2 (中) | 一般服务故障或部分功能异常 | 1小时 | 8小时 | 值班 → 主管 |
| P3 (低) | 轻微问题或优化建议 | 1工作日 | 3工作日 | 值班 |

## RPO/RTO 实现策略

### 高可用实现

| 策略 | 适用服务 | 效果 |
|------|---------|------|
| 多可用区部署 | 所有核心服务 | 单可用区故障自动切换 |
| 主从复制 | PostgreSQL, Redis | 主库故障快速切换 |
| 集群部署 | EMQX, Kafka, ClickHouse | 节点故障不影响服务 |
| 无状态设计 | 后端 API, 前端 | 任意实例可处理请求 |
| 负载均衡 | 所有 HTTP 服务 | 自动剔除故障节点 |

### 数据保护实现

| 策略 | 适用数据 | RPO |
|------|---------|-----|
| 同步复制 | PostgreSQL 核心数据 | 0 |
| 异步复制 | PostgreSQL 非核心数据 | < 1分钟 |
| 消息持久化 | Kafka, EMQX | < 5分钟 |
| 定时备份 | 所有数据库 | < 1小时 |
| PITR (时间点恢复) | PostgreSQL | < 5分钟 |
| 异地备份 | 所有重要数据 | < 24小时 |

### 灾难恢复实现

| 策略 | 适用场景 | RTO |
|------|---------|-----|
| 自动故障转移 | 单节点/单可用区故障 | < 5分钟 |
| 手动故障转移 | 全区域故障 | < 1小时 |
| 备份恢复 | 数据损坏/误删除 | < 4小时 |
| 备用集群 | 主集群完全不可用 | < 1小时 |

## RPO/RTO 验证

### 验证方法

1. **故障注入测试**
   - 定期进行混沌工程测试
   - 模拟各种故障场景
   - 测量实际 RTO/RPO

2. **灾难恢复演练**
   - 每季度进行一次完整演练
   - 验证恢复流程有效性
   - 记录实际 RTO/RPO

3. **监控告警**
   - 实时监控服务可用性
   - 故障发生时自动计时
   - 生成 RTO/RPO 报告

### 验证频率

| 验证类型 | 频率 | 负责人 |
|---------|------|--------|
| 单节点故障注入 | 每月 | 运维团队 |
| 单可用区故障演练 | 每季度 | 运维团队 + 开发团队 |
| 全集群灾难恢复演练 | 每半年 | 全团队 |
| 数据恢复演练 | 每季度 | DBA |
| RPO/RPO 指标审计 | 每月 | 运维主管 |

## 例外和豁免

### 计划内维护

- 计划内维护不计入 RTO
- 需提前 48 小时通知
- 维护窗口：每周日 02:00-06:00

### 不可抗力

- 云服务商大规模故障
- 自然灾害
- 网络中断（非本平台原因）
- 上述情况不计入 RTO，但需记录和复盘
